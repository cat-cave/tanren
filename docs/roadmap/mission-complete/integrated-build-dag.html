The reframe

Time estimates are a proxy for node count. We measure the graph.

Every pitch quoted "engineer-months." That vocabulary assumes a fixed workforce. Tanren's own 95+ runs happened in ~2 months because the work is a graph of nodes executed in parallel by agents. So we discard duration and keep the two numbers that actually govern velocity:

METRIC · WIDTH

Parallel width

How many nodes can run at once. After the spine is frozen, ~110 feature nodes have no cross-bucket edge to each other — they are one fan-out. Width is bounded by build capacity (subagents + shelled-out codex/grok/glm), not by sequence.

METRIC · DEPTH

Critical-path depth

The longest chain of hard dependencies. It runs spine contracts → spine implementations → consumer MVP → apex proof — roughly 5 gated waves. Depth, not total node count, is the real floor on wall-clock.

The whole strategy in one line: freeze the 8 shared contracts first (small, co-designed, serial-ish), then the 142 nodes become a wide, shallow fan-out that a workflow drives at maximum parallelism — turning "years" into a bounded-depth graph.
The spine · critical path

Eight contracts every bucket builds-or-consumes.

These are not features — they are the shared interfaces. Each is co-authored by the buckets that need it, frozen once, then depended on. Get these right and the two biggest buckets (runtime + merge-queue) parallelize cleanly; get them wrong and you build competing authorities and duplicate proof stores. This is the single highest-leverage work in the plan.

Cross-feature seams · more than the sum

Where the six become one product.

These are the edges that a bag-of-tools can never have. Each is an explicit merge point the pitches independently arrived at — the reason tight self-integration beats Mergify + open-design + better-t-stack + GitHub CI as separate purchases.

SEAM 1One fragment kernel

Template, verification, design, integration, and governance fragments all run on one extracted Writer-owned F2 kernel (ds-3 · rv-3 · in-7 · bh-19 · gv-10) — plan→write→validate→compose, mandatory base, no silent fallback. Bodies/schemas stay separate. Build the kernel once; five families inherit it.

SEAM 2A4 render ≡ demo engine

The design oracle's pre-merge visual verification (ds-4) and the post-merge demo (rv-18 · ds-6) are the same live-render substrate — the repo's missing WS-D4a — replaying the same scenarios pre- and post-deploy. Build the render harness once; the gate and the demo both consume it.

SEAM 3One trace ID, end to end

Forge sentence → persona/behavior → DesignContract → fragment → source → rendered scenario → gate → integration node → MergeAuthority → deploy → per-behavior demo → post-deploy re-proof all carry one causal ID. Personas/behaviors are the toggles in the design preview, the axes of the tests, and the assertions in the demo — one object, many consumers.

SEAM 4Behaviors → tests, for free

Because behaviors are first-class platform objects, the executable-test compiler (rv-2) isn't a bolt-on — it falls out of the data model, and feeds the merge-queue bisection (rv-16 · mq-3) and the back-half symptom check (bh-5) with no second test stack.

SEAM 5One Authority pattern, three heads

MergeAuthority-V2 (land), ResolutionAuthority (declare fixed), PromotionAuthority (deploy) are the same fail-closed pattern over the same proof substrate (mq-2 · bh-11 · gv-29). Governance parameterizes their inputs; none competes to land code.

SEAM 6One extended DeployAdapter

Preview/canary/promote/rollback/digest-attestation (SP·6) is needed by runtime preview, back-half production re-proof, integration delivery, design demo, and governance promotion. One contract, five consumers — today it's five separate "deferred" stubs.

SEAM 7Audit finding ↔ new spec

Governance's finding→spec materialization (gv-16) is the formal, atomic version of the back-half audit→spec loop (bh-2). Governance owns the disposition ledger + dependency-correct edges; back-half owns the writer/gate/deploy execution the routed spec flows through. Same loop, split cleanly.

SEAM 8One proof substrate, all exports

Every bucket emits into the CAS/Merkle proof store (SP·3) and exports signed, offline-verifiable bundles (rv-24 · mq-15 · bh-33 · gv-32 · in-21 · ds-5). A customer can independently verify a behavior proof, a merge decision, a resolution certificate, or a design system — one substrate, one tanren … verify CLI family.

Build waves · maximum parallelism

Depth-5 graph, executed as waves.

The DAG has ~5 gated levels. Within each wave, nodes run concurrently across worktrees. The three serialization barriers — migrations 0033–0040, the event registry, and screens.ts/nav — are the only forced single-file bottlenecks; everything else fans out.

The workflow · execution

The DAG is the workflow.

This graph maps directly onto a Tanren Workflow: phases = waves, and each wave is a parallel()/pipeline() fan-out over its nodes. Every node is one worktree-isolated spec; capacity is elastic because we shell out to codex/grok/glm as extra build+audit agents — we are not workforce-bound.

  • Node = spec = worktree. Each of the 142 nodes becomes one PR-sized spec built by a subagent (or a shelled-out codex/grok/glm agent) in an isolated worktree, gated on green just ci + apex-relevant conformance before merge — the exact discipline in docs/playbooks/parallel-orchestration.md.
  • Wave 0 is a judge-panel, not a fan-out. The 8 spine contracts are co-designed by independent agents proposing + adversarially reviewing each interface, because a wrong contract poisons every consumer. Freeze them behind conformance suites before any Wave-1 implementation starts.
  • Barriers are explicit stages. The three serialization points (migrations 0033–0040, event registry, screens.ts) are single-owner pipeline stages every touching node routes through — never concurrent edits. Everything else runs at min(16, cores-2) width per workflow, chained across waves.
  • Adversarial verification per node. Each built node is verified by a second agent (a different model — grok/glm/codex) against its pitch's validation column + a negative control, before it counts as done. Quality scales with capacity, not sequence.
  • Self-hosting endgame. Once Wave 2 lands, Tanren builds Wave 4 on itself: each full-tier node becomes a spec Tanren drives through its own (now never-blockable, behavior-verified) pipeline — the plan's own proof of usefulness.
