# in-22 — integration evidence producer, readers, and attestation

## Goal

Complete the existing in-19 A3 delivery path rather than add a second probe.
After in-19 has independently observed the real product effect, the live delivery
flow durably records its exact integration validation proof and seals a portable
`integration-evidence.v1.dsse.json` attestation. A reader can resolve every link
without a mutable current-binding pointer; one mismatch seals nothing.

## Production call graph

For an individual delivery:

`DeliveryStages.reconcileBinding → PgDeliveryBindingSetSealer →
PgIntegrationRuntimeAttachmentRecorder → DeployOnMergeWatcher → in-19 A3
DemoOnDeployWatcher → DeliveryStages.recordEvidence →
IntegrationEvidenceAttester`.

The recorder persists the sealed binding generation against the authorized merge
SHA and emits `integration.runtime.attached` before deploy. The existing land-group
flow seals through its same `GroupDeliveryA3Gate` before production promotion, then
uses the same attester after the group’s A3 observation. Group `deploy.verified`
now carries `sourceRef`, the authorized group merge SHA, because it has no separate
per-run `deploy.triggered` event.

## Durable proof and readers

Migration 0108 extends the pre-existing FORCE-RLS `integration_validation_proofs`
table with the channel/template digest, negative-control checklist, proof bundle
identifiers, byte digest, signing key ID, and DSSE envelope. It also adds FORCE-RLS
`integration_runtime_attachments` and redacted `integration_evidence_failures`.

The seven `PgIntegrationEvidenceReaders`, each using `runWithOrgScope`, resolve:

1. delivery row plus authorized `merge.completed` SHA;
2. release-required requirement, sealed binding generation, behavior, grant, and
   channel/template digest;
3. pre-deploy binding-generation attachment;
4. verified deployment and its authorized SHA;
5. one passed post-merge behavior verdict;
6. one immutable independent in-19 observation with correlation and provider receipt;
7. active (or revoked) grant generation.

`assembleIntegrationEvidence` requires exactly one value at every cardinality and
byte-matches merge SHA, binding generation, deployment, behavior, provider,
correlation, channel/template digest, and grant generation. A revoked grant writes
a durable, fixed redacted failure. Any absent, duplicate, stale, or mismatched key
returns a blocked result before proof ingestion, bundle persistence, or proof-row
write.

## Attestation and offline verification

`IntegrationEvidenceAttester` ingests the sanitized exact observation through the
shared `PgProofSubstrate`, constructs and verifies the proof bundle, signs DSSE PAE
with its production Ed25519 identity, and only then inserts the authoritative
validation proof. `tanren integrations verify-evidence <bundle.json>` independently
recomputes canonical payload bytes, the Merkle proof root, bundle digest, bytes
digest, bundle identity binding, and both Ed25519 signatures. It never trusts a
stored validity field.

## Negative controls and verification

1. A deploy SHA or attachment-generation mismatch cannot produce ready evidence;
   the delivery completion gate degrades without a `delivery.completed` attestation.
2. A real Postgres test reads a known org-B attachment while scoped to org A and
   receives zero rows; it also asserts FORCE RLS on all durable evidence tables.
3. The CLI test signs a valid DSSE/bundle, then changes the payload; recomputation
   rejects its broken bundle binding and DSSE signature.

Required handoff gates are `just fast-check`, `just types-lint`,
`just architecture`, `just schema-drift`, the full CI gate, and coverage at or above
75.5% excluding the opt-in RLS suites.
