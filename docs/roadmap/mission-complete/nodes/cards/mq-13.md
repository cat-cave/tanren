# mq-13 — Deploy/verify/demo/rollback loop extension

**Phase**: full (merge-queue)

**Node ID**: mq-13

**Deps**: mq-5, mq-10 · SP-5, SP-6

**Node credit**: 0 until independent audit + green gates + merge.

## Purpose and boundary

Turn a completed land group into one durable proof-backed delivery loop: group artifact, preview deploy/verify/demo, promotion, production demo, then rollback or repair routing when evidence says production regressed. It extends `DeployAdapter` in `services/orchestrator/src/engine/contracts/deployAdapter.ts` (including `buildArtifact`, `applyPreview`, `promote`, `rollback`, and `teardownPreview`) and the current post-merge chain in `engine/postMerge/subscriber.ts`.
It neither invents a deployment adapter nor bypasses `MergeAuthorityV2`.

It builds on the merged mq-5 completion seam: `multiMemberLandGroupPg.ts:landAuthorizedGroupPg` -> `landGroupStore.ts:PgLandGroupStore.completeOnClient` -> `appendCompleted` -> existing `merge.land_group.completed`. It preserves `DemoOnDeployWatcher.check` and `proofBackedWebDemo.ts:buildProofBackedWebDemo`; it preserves rv-19's `PostMergeReproofCoordinator` as owner of later behaviour reproof and existing `deployment.promoted` / `deployment.rolled_back` outcomes.

## Production call graph

Today `startPostMergeSubscriber` calls `PostMergeSubscriber.runChain(runId)`, isolating `watcher.check`, `deployWatcher.check`, and `demoWatcher.check`; worker startup builds those watchers in `engine/worker/autonomyLoops.ts`. `DemoOnDeployWatcher.check` requires `deploy.verified` before `ProofBackedWebDemo.demo`.

The one new production entry point is `LandGroupDeliveryLoop.check(runId)`, first in `PostMergeSubscriber.runChain`. For a member whose `land_groups` row is complete, it resolves exact group/main SHA, uses the adapter to build one artifact, apply preview, verify, and call `ProofBackedWebDemo.demo`; only then it promotes, verifies production, and demos production. Group members' current per-run deploy/demo watchers receive membership guards and no-op, so a group cannot deploy once per member.
On a failing production proof it calls the adapter's real `rollback` to persisted prior-good release, not merely rv-19's release-pointer reconciliation. Attribution to one member may call mq-10's `PgAutonomousRepairRouter` only after causal replay; otherwise the loop is `needs_attention`.

## Contract / Data model

Add `LandGroupDeliveryReceiptV1Schema` (strict Zod, frozen `schemaVersion: "land_group_delivery.v1"`) for group ID, completed main SHA, ordered member run IDs, artifact CAS digest, preview/production/rollback release IDs, state, and idempotency key. It is a receipt, not a deployment API.

At the next free migration slot at build time, add FORCE RLS `land_group_delivery_loops`: `(org_id, land_group_id)` unique, durable state, `project_id`, `main_sha`, artifact digest, release lineage, receipt JSON, and idempotency key. Use composite FKs to existing `land_groups`, `projects`, `release_instances`, and `cas_artifacts` as applicable.
As existing `land_groups` has no `project_id`, creation derives and verifies project ownership through authority decision/member run before persisting; do not assume a nonexistent group-project FK.

The loop consumes existing `merge.land_group.completed`, `deploy.triggered`, `deploy.verified`, `deploy.failed`, `demo.evidence.recorded`, `demo.completed`, `demo.failed`, `deployment.promoted`, and `deployment.rolled_back`. Register `merge.land_group.delivery.completed` and `.failed` through the serialized event-vocabulary barrier before emission; all events append only by `EventStore`.

Expose `GET /orgs/:orgId/projects/:projectId/merge-queue/land-groups/:landGroupId/delivery` from the merge-queue route family. Extend existing Merge Queue with a read-only group delivery timeline: artifact, preview evidence, promotion, production evidence, rollback/repair disposition, and receipt ID.

## Fail-closed proof

Invariant: exactly one delivery receipt/artifact per completed group, no promotion until that group's preview verification and proof-backed demo pass, and no production rollback claim unless `DeployAdapter.rollback` succeeds. The gravest prohibited fail-open is deploying or promoting separate members (or a failed preview) as if the whole land group had been verified.

Local verification sends duplicate post-merge notifications and proves idempotent one-row, one-artifact delivery; it fails preview evidence and proves no promote plus preview teardown. The independent adversarial GO fails a production behaviour after promotion: the adapter rollback must be called with persisted prior-good lineage, group state must be failed/rolled back, and no repair target is fabricated. A no-prior-good negative control ends `needs_attention`, never pretends rollback succeeded. Audit compares receipt SHA/members/digest to `land_groups`, release rows, and EventStore chronology.
