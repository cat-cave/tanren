# in-20 — Full HTTP surface + generated API schemas

**Phase**: MVP (integrations)
**Node ID**: `in-20`
**Deps**: in-1, in-2, in-3, in-4, in-10, in-15, in-17 (all merged),
in-19 (in flight — A3 live trigger/observe + effect probe + negative controls)
**Node credit**: **0** until independent audit, full green gates, and merge

## Purpose and boundary

Expose the **complete integration read surface** as a first-class, versioned,
GET-only HTTP API with **generated + drift-gated JSON-Schema artifacts**, matching the
rv-22 read-surface pattern exactly. Today the integration HTTP surface is partial and
scattered: a connection-inventory list (`GET /:orgId/integrations`,
`routes/integrations/index.ts:141`), a redacted event feed (`GET
.../integration-events`, `integrationEventsRead.ts:67`), a contract catalog (`GET
.../integration-contracts/catalog`, `routes/integrationContracts/index.ts:54`), a
metrics read (`routes/integrationMetrics/index.ts:37`), and an operation-status read
(`authorityWrites.ts:343`) — but there is **no HTTP route** over
`integration_requirements`, `capability_nodes` (in-9/10/17), `integration_bindings`
(in-14/15), or the post-merge delivery DAG (in-17/19). The in-3 lifecycle inventory
exists only as an optional side-field on the connections list, gated behind a
`projectId` query param (`routes/integrations/index.ts:157`), not a first-class
endpoint. And **none** of these integration responses have generated schemas in the
central export catalog (`engine/schemaExport/catalog.ts:101` currently emits only
`IntegrationsManifestV1`). in-20 completes the read API + registers every response as a
generated, drift-checked schema.

Boundary: in-20 is **read-only + schema generation**. It does NOT add or change any
command/write route (link/rotate/provision/selection live in
`routes/integrations/authorityWrites.ts` + `index.ts` and stay untouched), does NOT
weaken any RLS/org-scope guard, and does NOT expose secrets, tokens, or unredacted
payloads (the event feed's redaction, `integrationEventsRead.ts`, is the model). It
reuses the frozen contracts (`IntegrationRequirementV1`, `IntegrationBindingContractV1`
at `contracts/integrationBindingContract.ts:2`, the delivery vocabulary at
`events/schemas/deliveryVocabulary.ts`) — it does not invent new domain shapes.

draft-2020-12 ...)` (the exact rv-22 shape, `routes/runtimeVerification/contract.ts:45-169`).
Mounting adds **one** `app.route("/v1/orgs", …)` line near
`mountFeatureRoutes.ts:339` (the serialized shared file — serialize this PR against
other route additions).

## Contract / Data model

No migration and no new tables — in-20 is a projection over existing integration
tables. Response schemas are new **Zod** contracts in `routes/integrations/contract.ts`
+ registered in the central `engine/schemaExport/catalog.ts` (extend the `integrations`
family, `:101`) and/or a local render catalog mirroring
`runtimeVerification/contract.ts:156`. Generated JSON-Schema artifacts are emitted to
`contracts/json/**` by `scripts/contract-schema-export.mjs` (families incl.
`integrations`), and a committed compatibility baseline (e.g.
`contracts/integration-read-compat/v1.json`, per the rv precedent
`contracts/rv-read-compat/v1.json`) is drift-gated by a new test mirroring
`services/orchestrator/tests/verificationReadCompat.test.ts:16` + the
`check:contract-schema-drift` script (`package.json:11`). Every response is redacted
(no tokens, principal secrets, or raw payloads); the binding response carries the
`appEnvHash` proof (in-15), never the resolved env.

## Provable / callable / visible

- **Provable**: reads emit nothing new (GET-only); the generated schema set + the
  committed baseline are the durable artifacts, and the drift check is the proof they
  stay in sync with the Zod source.
- **Callable**: `GET /v1/orgs/:orgId/projects/:projectId/integrations/lifecycle`
  (first-class in-3 inventory rollup), `.../integration-requirements`,
  `.../capability-nodes`, `.../integration-bindings` (with `appEnvHash` proof),
  `.../delivery` (in-17/19 delivery-DAG status), each org+project-RLS-guarded; the
  existing legacy `/orgs` read routes remain (clean-replace applies to NEW surface, not
  a churn of the shipped ones unless in-20 supersedes one — if it promotes the in-3
  side-channel to a first-class endpoint, remove the side-field to avoid two sources).
- **Visible**: the responses back the in-21 Integration Control Center UI (in-20's
  downstream) and are exportable via the generated JSON-Schema catalog.

## Fail-closed proof

The invariant: every integration read is org+project-scoped through `runWithOrgScope`
(RLS denies by default), redacted, and its response shape is exactly the generated
schema. The gravest fail-open is a cross-tenant read (a missing `withOrgScope`/access
guard leaking another org's connections, requirements, bindings, or delivery state) or
leaking a secret/token/unredacted payload. Independent adversarial GO injects: (a) a
cross-org caller hitting each new endpoint → zero rows under the non-superuser
`tanren_app` role; (b) a non-member of the project → `403`/`404`, never data; (c) a
response asserted to carry no token/secret/raw payload field; (d) a
`--check` schema-drift run after a deliberate Zod edit → the drift test FAILS (proving
the generated schemas are load-bearing, not decorative). RLS proofs run as
`tanren_app` and are wired into a `smoke-rls-*` recipe.

## Size / migration

Target 700–1000 lines (this is a `big:true` node, `build-workflow.mjs.txt:125`) across
`routes/integrations/reads.ts`, `routes/integrations/contract.ts`, the
`schemaExport/catalog.ts` `integrations`-family additions, the committed baseline +

`schemaExport/catalog.ts` (shared) and NOT `screens.ts`/`main.ts`.

## Acceptance

1. Every integration domain surface (lifecycle inventory, connections detail,
   requirements, capability nodes, bindings-with-proof, delivery-DAG status) is
   readable via a `/v1/orgs/:orgId/projects/:projectId/...` GET route, org+project-RLS
   guarded and redacted.
2. Each response has a generated JSON-Schema artifact registered in the export catalog,
   a committed compatibility baseline, and a drift check that fails on an
   unsynchronized Zod edit.
3. Cross-org and non-member reads return zero data; no token/secret/unredacted payload
   appears; focused route/RLS tests plus `just fast-check`, `just ci`, and `just smoke`
   pass before audit GO.

## CRITICAL sequencing

in-20 **depends on in-19** (in flight — A3 live trigger/observe + effect probe +
negative controls). in-19 produces the delivery-DAG live-trigger/observation state that
in-20's `.../delivery` read surface projects; in-20 must consume in-19's FROZEN
delivery/observation shape (`engine/postMerge/delivery/*`,
`events/schemas/deliveryVocabulary.ts`) — do not guess it before in-19 lands. All other
deps (in-1..4, in-10, in-15, in-17) are merged; reuse their shipped repositories/stores
(the survey enumerates them) rather than re-deriving reads. in-20 is itself the
dependency of in-21 (Control Center UI) — its schemas are that UI's contract, so freeze
the response shapes deliberately.
