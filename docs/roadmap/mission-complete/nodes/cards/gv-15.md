# gv-15 — Governance Studio UI

**Phase**: governance MVP
**Node ID**: `gv-15`
**Deps**: gv-7..14 · SP·8
**Node credit**: **0** until independent audit, green gates, and merge

## Purpose and boundary

Give operators one visible, project-scoped Governance Studio for the durable
governance facts already owned by gv-7..14. The Studio reads append-only policy
revisions, immutable tiers and bindings, and an exact effective-policy receipt;
it authors revisions and activates/binds through the existing governance command
routes. It has no local policy store, client-side policy decision, direct DB
access, synthetic receipt, or alternate mutation route.

The survey found a production-wiring defect in the dependency surface: the
existing `mountGovernanceRoutes` factory was constructed by the Forge route
factory but never invoked from `mountFeatureRoutes`. gv-15 owns the one-line
production mount because a dashboard client must not claim existing HTTP
authority that production has not actually exposed.

## Dependencies and authority

- gv-7: `POST /governance/revisions`, `POST .../activate`, and `GET .../revisions`
  are the only policy-revision author/lifecycle authority.
- gv-8/gv-9: `GET .../tiers`, `GET .../bindings`, and `POST .../tiers/:tierId/bind`
  own tier activation and the one-active-binding transition.
- gv-9: `GET .../effective/:subjectKind/:subjectId` is the exact immutable
  effective-policy receipt reader. It is intentionally not treated as a list
  endpoint.
- gv-10/gv-13/gv-14: the existing fragment authoring, validation, and
  org-admin/RLS command guards remain server authority.

## Production call graph

`createApp` → `mountFeatureRoutes` → `buildForgeRouteAnswererFactories` →
`forgeAnswerers.mountGovernanceRoutes(app)` → `mountGovernanceRoutes` →
`createGovernanceRoutes` → org/project authorization + `runWithOrgScope` →
gv-7..14 stores/routes.

`dashboard createApp` → `mountScreens` → `mountGovernanceStudioScreen` →
`GovernanceStudioClient` → the same org/project governance HTTP routes. Author,
lifecycle activation, and tier binding use `clientDepsFor` so the BFF forwards
the session CSRF token; the dashboard never writes a policy directly.

## Fail-closed behavior

- Revisions, tiers, and bindings are all schema- and scope-validated. Any
  unavailable, malformed, cross-project, duplicate, dangling, or multiple-active
  response is a single loud unavailable state; it is never rendered as an empty
  or active policy.
- A zero-active-binding response is a valid, explicit **unbound** state, not an
  active default. A known active binding must resolve to its exact tier and hash.
- The default receipt coordinate is the active binding's exact
  `activation/<bindingId>` receipt. A custom lookup requires nonblank, typed
  `subjectKind` and `subjectId`; `404`, malformed, and unavailable each remain
  visibly non-successful.
- POST gates trim and reject blank/wrong-type form values before any authority
  call. Activation/binding IDs and optional parent IDs must occur in the freshly
  validated read model before a command can be sent.
- A command success is shown only after its exact response coordinate parses and
  the reloaded model confirms the created revision or active binding. A failed
  confirmation is `unknown`, never success.

## Negative controls

1. A revisions/tier/bindings read failure or malformed payload renders
   `data-governance-studio-unavailable`, with no lineage or fabricated active
   binding.
2. Two active bindings, a binding whose tier is absent, or a hash mismatch makes
   the Studio unavailable rather than choosing one.
3. Empty, malformed JSON, foreign project, unknown parent/revision/tier, and
   blank receipt coordinates make no governance command call.
4. A receipt `404` remains `not found`; it does not render a policy body.
5. A bind response whose binding/tier coordinate differs from the request, or a
   post-command reload that cannot prove the effect, remains an unknown outcome.
6. The production mount test constructs the actual feature-route mount and proves
   all governance routes are registered; it does not hand-mount a fake route.

## Acceptance

1. `/governance` is a permanent dashboard nav surface with project selection and
   visible revision lineage, every binding, exact active-binding status, tiers,
   and a real effective-policy receipt.
2. The raw fragment-config author form, revision lifecycle activation, and tier
   binding form all invoke only existing org-admin governance command routes.
3. Production constructs the governance route factory; dashboard tests exercise
   the real `createApp → screens` path and its HTTP client routes.
4. No migration; no edit to `LEDGER.md`; all source files remain below 500 lines.
